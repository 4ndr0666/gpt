Section 1

Comprehensive Definition

Context engineering is the discipline of deliberately designing everything that enters an AI model's context window at the moment it works on your task — and everything that stays out. It is broader than prompt engineering: prompt engineering tunes the wording of one message; context engineering designs the entire information supply chain the model relies on across a task, a run, or a whole system.

The complete definition has five layers, and a context engineer is responsible for all of them:

  1. Instructions — the role, the goal, the constraints: your system prompt and task brief.
  2. Knowledge — documents, examples, and retrieved facts the model cannot know on its own.
  3. State — conversation history, prior decisions, memory files, what happened on previous runs.
  4. Tools — the schemas the model reads to act, and the outputs it reads back after acting.
  5. Output contract — the exact shape, format, and destination of the response you will accept.
Context starvation — too little input
The model improvises, guesses, and hallucinates to fill the gaps.
Context rot — too much input
Attention dilutes, instructions get buried, quality silently drops while cost and latency climb.

The craft is staying in the narrow band between the two: minimum sufficient context, structured so the model can find what matters. Nearly every serious agent failure you will ever diagnose eventually reduces to one of these two modes.

Section 2

Powerful Usage You're Missing Out On

For your profile — someone who runs agents on a schedule — the highest-leverage pattern is the self-contained brief with just-in-time pointers. Instead of pre-stuffing every fact into a task prompt, you write the brief to reference durable state and instruct the agent to fetch it at run time: "Read /home/z/my-project/worklog.md before starting. Do not repeat concepts from previous runs." Three compounding benefits:

Briefs stay small and cheap — you pay for pointers, not payloads. Context is always current — a file read at run time beats a fact frozen at write time. Runs become resumable and auditable — the agent reconstructs full situation from state you can open and inspect yourself.

The second underused move is setting explicit context budgets: brief ≤ 150 words, memory = only the worklog file, examples = at most two. Budgets force the curation decisions you would otherwise skip — and curation is where the quality comes from.

The principle underneath both moves: an autonomous agent's output quality is bounded by the quality of the context you hand it — not by the cleverness of its prompt. Your twice-daily loop will only ever be as good as the brief that launches it.

Section 3

The Common Misuse

Context stuffing — the kitchen-sink prompt

The failure pattern: paste the entire chat transcript, attach whole files "just in case," add every background detail you have — and hope more information produces better answers. It produces worse ones. Past a saturation point, model attention degrades measurably: instructions placed in the middle of long contexts are reliably missed (the "lost in the middle" effect), conflicting instructions multiply, outputs get longer and more generic, and token cost and latency rise in proportion to the noise you added.

Three signs you are doing it:

  • The model ignores instructions — because you gave it fifteen, and some of them conflict.
  • Outputs feel boilerplate — the specifics you "provided" are diluted in sheer volume.
  • You re-explain the same requirements every message — because nothing durable anchors them.

The fix is curation, not accumulation: include the minimum sufficient context, structure it with labeled sections, place critical instructions at the beginning and the end, and convert anything large into a pointer the agent fetches just-in-time. Rule of thumb: if the model can go read it at run time, don't paste it.
